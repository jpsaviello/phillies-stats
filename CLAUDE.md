# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev         # start Vite dev server with HMR
npm run dev:server  # start the backend API proxy (server/) on :8080 — needed for any data to load
npm run build       # type-check then bundle the frontend (tsc -b && vite build)
npm run lint        # run Oxlint
npm run preview     # serve the production build locally (still proxies /api to :8080)
```

Local dev requires **both** servers: `npm run dev:server` in one terminal, `npm run dev` in another. Vite proxies `/api` to `localhost:8080` (see `vite.config.ts`). The backend builds separately: `npm --prefix server run build`.

No test runner is configured.

## Architecture

This is a single-page React 19 + TypeScript app (Vite, Tailwind v4) that displays Philadelphia Phillies stats from the public MLB Stats API, plus live odds from The Odds API. All external API calls go through a small backend proxy (`server/`) so no keys ever reach the client bundle.

**Data flow:** `src/api/mlb.ts` → `src/utils/cache.ts` → `/api/*` (backend proxy) → upstream API → component → render. There is no state management library and no data-fetching library; each tab component still owns its own fetch lifecycle via `useEffect` + `useState`, and the cache sits *below* them at the single `get()` helper in `mlb.ts`, so no component had to change to benefit from it (see Request cache below).

- **`server/`** — standalone Hono + Node backend (own `package.json`, not a workspace). `server/src/index.ts` defines `GET /api/health`, `GET /api/mlb/*` (allowlisted passthrough to `statsapi.mlb.com` — only paths starting with `/teams/`, `/stats`, `/standings`, `/schedule`, `/people/` (→ `api/v1`) or `/game/` (→ `api/v1.1`, the live-feed endpoint's version) are forwarded; the prefix→base mapping lives in `MLB_ALLOWED` in `core.ts`), and `GET /api/odds` (holds `ODDS_API_KEY`, 30-min in-memory cache shared across all visitors); `server/src/chat.ts` adds `POST /api/chat` (see Chat bot below); `server/src/auth.ts` adds `POST /api/signup`, `POST /api/login`, `POST /api/logout` and `GET /api/me`, backed by `db.ts` (Neon `pg.Pool`), `crypto.ts` (scrypt/token hashing), `cookies.ts` (Set-Cookie build/parse) and `authRateLimit.ts` (see Auth below); `server/src/favorites.ts` adds `GET /api/favorites`, `POST /api/favorites/add` and `POST /api/favorites/remove` (see Favorite players below); `server/src/notifications.ts` adds `GET /api/notifications/daily` (cron-triggered, `CRON_SECRET`-authenticated) and `GET`/`POST /api/notifications/unsubscribe` (unauthenticated, token in the query), backed by `email.ts` (SendGrid) and `emailTemplates.ts` (see Notification emails below). Dev runs via `tsx watch` loading `../.env.local`; prod is `tsc` → `node dist/index.js`.
- **`src/api/mlb.ts`** — all client-side API calls, now against `/api/mlb` and `/api/odds`. Constants at the top: `PHILLIES_ID = 143`, `SEASON = 2026`. Each export maps to one MLB Stats API endpoint, plus `fetchOdds` for betting lines. Note: the `gameLog` stats endpoint (`fetchGameLog`) returns a player's full-season splits in **chronological** order (oldest first) — `fetchGameLog` passes them through unchanged; `GameLogModal` slices the last 10 (reversed to most-recent-first) for its table and feeds the full season to the trend chart. Don't assume MLB Stats API endpoints are reverse-chronological by default; this one isn't. `fetchSplits(personId, group)` hits the same `/people/{id}/stats` path with `stats=statSplits&sitCodes=vl,vr,h,a` for a player's situational splits (vs LHP/RHP, home/away); the API can omit individual sitCodes (or fields within a split's `stat`) for tiny samples, so `GameLogModal` orders by the requested codes, filters out missing ones, and renders absent fields as blank rather than assuming all four are present.
- **`src/types/mlb.ts`** — TypeScript interfaces for API response shapes (`Player`, `BattingStats`, `PitchingStats`, `RosterEntry`, `StandingsRecord`, `GameLogSplit`, `BattingGameStat`, `PitchingGameStat`, `StatSplit`). `StatSplit` reuses the full `BattingStats`/`PitchingStats` shape under `stat` (statSplits returns season-stat objects), keyed by a `split.code` discriminator.
- **`src/data/allStars.ts`** — hardcoded roster for `AllStarBanner`; update manually each season/selection, not fetched from an API.
- **`src/App.tsx`** — root component; reads the active tab from the URL via `useRoute()` and conditionally renders the tab components.
- **`src/components/`** — one file per tab: `BattingTable`, `PitchingTable`, `Standings`, `Schedule` (each upcoming row's right-hand slot shows first pitch time via `src/utils/gameTime.ts`'s `firstPitch(game)`, replacing the old `detailedState` string — gated on `abstractGameState === 'Preview'`, **never** `detailedState === 'Scheduled'`, because MLB flips `detailedState` to `Pre-Game` a few hours before first pitch and a `Scheduled`-only check would miss that window; `firstPitch` returns `null` for `Postponed`/`Cancelled`/`Suspended` games since a postponed game keeps its original `gameDate` and would otherwise print a first pitch that's never happening, `'TBD'` when `status.startTimeTBD`, and `null` for `Live`/`Final` so the row falls back to `detailedState` unchanged), plus `Header`, `Nav`, `AllStarBanner`, `HeroStrip` (summary-card strip above the Nav on every tab — record/last game/next game/team leaders; owns its own fetches and renders nothing if any MLB fetch fails), `LiveGameStrip` (mounted above `HeroStrip`, renders **only while a Phillies game is live** — score/inning/count/current matchup from the v1.1 live feed via `fetchLiveFeed`, trimmed to ~400B with MLB's `fields=` param; two-tier polling: today's schedule every 60s gates a 15s feed poll, ticks skipped while `document.hidden`, all failures render nothing; `?liveGamePk=<pk>` in the URL bypasses the gate and renders any game's feed — finished games work, which is how the live rendering is tested deterministically), `DailyBriefing` (collapsible morning-briefing card between `HeroStrip` and `Nav`, fed by a routine-written static file — see Daily briefing below), `OnThisDayCard` (collapsible historical-moment card stacked directly below `DailyBriefing`, same routine-written-static-file pattern — see On this day below), `WildCardStandings` (NL Wild Card race table rendered by `Standings` **below** the NL East table — it is a standings table, not a schedule widget; it briefly shipped on the Schedule tab and was moved 2026-08-04 because that's where users look for it. It renders nothing on failure/empty, so it's mounted **outside** `Standings`' loading/error branches — a division-standings error doesn't take the wild card table down with it — and the gap between the two tables is the parent's `space-y-8` rather than a margin inside the component, so it collapses when the widget renders `null`. **As of 2026-08-13 it no longer fetches** — the fetch-and-tiebreak moved up into `src/hooks/useWildCardRace.ts`, owned by `Standings` and passed to this table and to `PlayoffPush` as props, because both state a playoff position from the same ordering (see Playoff Push below). Uses `fetchWildCardStandings` — `standingsTypes=wildCard` returns one league-wide group of every **non-division-leader** team, pre-sorted by `wildCardRank`, which means **the Phillies drop out of the response entirely whenever they lead the NL East**; the component handles `philliesIndex === -1` and otherwise extends its 7-row cutoff far enough down to always keep the Phillies' row visible. A "Playoff cutoff" divider row is drawn after rank 3, the NL's wild card berth count. **MLB's Stats API does not apply tiebreakers** — `wildCardRank`/`leagueRank`/`sportRank` break ties by ascending team ID, not the real 2022-CBA rules (head-to-head, then intradivision, then intraleague record), so the table's `#` column is **positional** (`i + 1`), never `r.wildCardRank`, and the rendered order intentionally diverges from MLB.com's own standings page whenever clubs are tied. Head-to-head isn't in the standings response at any hydration level, so ties inside the rendered window are resolved with one trimmed `fetchSeasonResults` call per tied club (from `/schedule`, Final games only), fetched **before first paint** — never as a re-sort of an already-painted table, which would visibly rearrange the cutoff line in front of the user. `hydrate=team(division)` on `fetchWildCardStandings` supplies the intradivision criterion but swaps `team.name` to the full club name, hence `team.teamName ?? team.name` for display. The grouping/ordering itself is the pure `src/utils/tiebreakers.ts` (`applyTiebreakers`/`teamsNeedingTiebreak`), written against a structural `TiebreakerRecord` shape so `Standings.tsx`'s NL East table — which has the identical `divisionRank` flaw but draws no cutoff line, so it wasn't worth fixing yet — could reuse it later. Criterion 4 (last half of intraleague games) isn't implemented; a group still tied after intraleague keeps the API's order. Any failure in the tiebreaker fetch degrades silently to the original API order with no `†` markers or footnote), `PlayoffPush` (pennant-race panel rendered by `Standings` **above** the NL East table — see Playoff Push below), `MatchupPreview` (pregame starting-pitcher panel rendered by `Schedule` **above** the game list — see Matchup preview below), `BullpenUsage` (recent-workload panel rendered by `PitchingTable` **above** its table — see Bullpen usage below), and `GameLogModal` (shared player-detail modal opened from a row click in `BattingTable`/`PitchingTable`). It shows, top to bottom: a season-line header of stat tiles (the row's already-loaded `BattingStats`/`PitchingStats` is passed in via the `seasonStat` prop — no extra fetch), a situational splits table (from `fetchSplits`), the rolling-trend chart, and the last-10-games table. The two fetches (game log for the chart/table, splits for the splits table) run in **separate** `useEffect`s and fail independently, so a splits error never blanks the trend/table. The tables' `selectedPlayer` state carries `{ id, name, stat }` so the season line can render immediately. `ChatWidget` is the floating chat bot (see Chat bot below), mounted once in `App.tsx` outside the tab conditionals so its history survives tab switches. `AuthWidget` is the sign-in modal, rendered inside `Header` rather than as a top-level sibling because its trigger button lives in the header row (see Auth below); its signed-in branch also renders the avatar/name button that opens `ProfileModal` (see User profile below). `StarButton` is the per-row favorite toggle and `FavoritesCard` the "Your Players" summary card — both render only when signed in (see Favorite players below). `ProfileModal` is the profile-editing sheet opened from `AuthWidget`, covering display name/phone/hometown, favorite player/jersey number/fan-since, notification prefs, and account management (password change, account deletion) — see User profile below.

**Tab routing** is a ~90-line hash router, `src/hooks/useRoute.ts` (no router dependency). The active tab and the open modal live in the URL — `#/standings`, `#/batting?player=592663`, `#/schedule?game=823017` — and `App.tsx` reads `tab` from `useRoute()` rather than holding it in state. The `Tab` union moved here from `Nav.tsx`, which now re-exports it so existing `from './components/Nav'` imports keep working.

Added 2026-08-26 because the app previously had no routing of any kind, which cost more than shareability: **the browser Back button always left the site**, so on a phone the back swipe after opening a player's game log exited the app instead of closing the modal.

Three things here are load-bearing. **First, hash-based, not path-based.** Path routing needs an SPA fallback rewrite configured on *both* deploy targets (nginx in k8s, `vercel.json`) or a hard refresh at `/standings` 404s; the hash needs nothing from either server and cannot break a deploy. **Second, modal state is derived from the URL, not synced to it** — `BattingTable`/`PitchingTable`/`Roster`/`Schedule` dropped their `selected*` `useState` and instead look the id up in their already-loaded rows. That's what makes a cold `?player=` link restore the modal for free once the fetch lands, and it means there's only one source of truth to disagree with. A player id that matches no loaded row renders no modal rather than erroring. **Third, closing a modal calls `dismiss()`, not `navigate()`** — `dismiss` pops the entry the modal's opening pushed (`history.back()`), because pushing a third entry would make Back immediately after closing land on the still-open state and *reopen* the modal, which is the exact behavior this router exists to fix. It falls back to `replaceState` when `history.state.appPush` is absent, i.e. on a cold load of a shared link where there is no entry of ours to pop and `back()` would leave the site.

Note `?liveGamePk=` is deliberately untouched — it's a query param on the real URL, not part of the hash, and remains LiveGameStrip's debug hook. Tab switches clear `player`/`game` via `setTab`, or a modal would reopen over an unrelated tab as soon as that tab's data loaded; the `enableRosterTab` flag-off redirect passes `{ replace: true }` so Back can't land on the now-hidden tab and bounce.

**Request cache:** `src/utils/cache.ts` — in-flight dedupe plus stale-while-revalidate, wired into the single `get()` helper in `mlb.ts` (and around `fetchOdds`/`fetchConfig`, which use their own `fetch`). It solves two problems that had one fix. Several components legitimately want the same data on one page load — `fetchBattingStats` alone is called by `HeroStrip`, `FavoritesCard` and `BattingTable` — and each was issuing its own identical request; sharing the in-flight promise collapses those without coupling components that are deliberately independent. And because every tab in `App.tsx` is an `&&` conditional, switching tabs unmounts the table and discards its data, so returning refetched from scratch and showed a skeleton for data the browser had held seconds earlier. Measured on a real cold load: **24 → 15 requests**, and **67 → 32** across a full tour of every tab and back.

Deliberately not a data-fetching library: `cached()` returns a plain promise, so the components' existing `useEffect` + `.then` shape is untouched. Only successes are stored, so a failed request leaves any previous value in place and retry buttons still reach the network. `maxStale` bounds the SWR window — past `ttl + maxStale` the caller waits for fresh data, without which a tab left open for hours would paint an hours-old value once before the refresh landed.

**The per-endpoint TTLs are correctness, not tuning.** `fetchLiveFeed` uses `NO_CACHE` (dedupe only, never a stored copy): it is polled every 15s and is the one thing in the app that must be current — caching it would silently freeze `LiveGameStrip`. `fetchSchedule` gets a 1-minute window rather than the 5-minute `STATS` default because `LiveGameStrip` polls the schedule every 60s to decide whether a game has started, and a 5-minute window would delay the live strip appearing by that much. Box scores get 1 minute since a box score can belong to a game still in progress.

**Odds integration:** `fetchOdds` (in `src/api/mlb.ts`) hits the backend's `/api/odds`, which holds the key (`ODDS_API_KEY` — runtime env var, never a `VITE_` build-time var) and caches upstream responses in memory for 30 minutes to stay within API rate limits. Locally the key lives in the gitignored `.env.local`; in k8s it comes from the `phillies-stats-odds` Secret (created imperatively with `kubectl create secret`, never committed, marked `optional` so the pod starts keyless). A missing key means `/api/odds` returns 503, and `Schedule.tsx` calls `fetchOdds().catch(() => [])`, so odds just don't render — it won't throw or block the schedule from loading. Odds are only shown for today's not-yet-finished game (see `getPhilliesOdds` in `src/utils/odds.ts`, shared by `Schedule.tsx` and `HeroStrip.tsx`), matched to the schedule by sorted home/away team name pair since the two APIs don't share game IDs.

**Chat bot:** `src/components/ChatWidget.tsx` (floating button bottom-right, full-screen sheet on mobile) sends text-only history to `POST /api/chat` via `sendChat` in `src/api/chat.ts`. The route (`server/src/chat.ts`) holds `ANTHROPIC_API_KEY` (runtime env var, same pattern as odds — gitignored `.env.local` locally, imperatively-created `phillies-stats-anthropic` Secret in k8s, `optional: true`) and runs a Claude tool-use loop (`claude-sonnet-5`, `@anthropic-ai/sdk` beta toolRunner, adaptive thinking, `effort: "low"`, `max_iterations: 8` — never send `temperature`/`top_p`/`top_k`; Sonnet 5 rejects them). Seven custom tools return trimmed JSON server-side: six fetch `statsapi.mlb.com` directly (schedule+probables, standings, batting/pitching season stats, player game log, single-game boxscore) and `get_odds` reuses `getOdds()` from `core.ts` (DraftKings moneyline + run line for the current slate, so it shares the same key and 30-min odds cache — keyless/upstream-fail returns `{"error":"odds unavailable (<status>)"}`). `get_game_boxscore` exists because the model otherwise **fabricated single-game player lines** — asked who led the team in hits, it attached a real box-score line to the wrong player, including one who didn't appear in the game. It takes a `gamePk` (which is why `get_schedule` emits one) and hits `/game/{pk}/boxscore`; note `chat.ts` calls `statsapi.mlb.com` directly, so the `/game/` → `api/v1.1` mapping in `MLB_ALLOWED` doesn't apply — the boxscore endpoint is `api/v1`. `teams.{away,home}.players` contains the **whole 26-man roster**, with empty `stats.batting`/`stats.pitching` objects for anyone who didn't play, so the trim keeps only entries where that object is non-empty and the system prompt states outright that a player absent from the boxscore didn't play. The prompt also forbids inferring a single-game line from season stats, game logs, or web search, and warns that game-log entries carry dates so the newest isn't necessarily today's game. Plus Anthropic's hosted **`web_search` server tool** (`web_search_20260209`, `max_uses: 3`) as the odds fallback: the system prompt tells the model to call `get_odds` first and fall back to `web_search` only when statsapi has no line (no game priced, or futures/division odds `get_odds` doesn't cover), scoped to Phillies/MLB. Because a server tool can end a turn with `stop_reason: "pause_turn"` and the beta `toolRunner` does NOT auto-resume that, the loop **iterates** the runner (rather than `await`ing it directly) and calls `runner.pushMessages(...)` on a paused turn — awaiting directly would silently truncate a web-search answer. Web search is billed per query (on top of tokens), so it's a real added cost on the fallback path; `max_uses` plus the per-IP/daily rate limits bound it. The loop and tool_use blocks never leave the server — only the final text does. Keyless → 503 and the widget shows a friendly "not configured" bubble (tagged `error: true` locally and **excluded** from later payloads). Client and server both enforce the caps (≤20 messages, ≤2000 chars); the client windows history with `slice(-20)` then drops leading assistant messages because the Anthropic API requires the first message to be user-role. The system-prompt date is computed in `America/New_York`, not UTC, so "today" doesn't roll over during night games.

`server/src/rateLimit.ts` bounds what chat can cost: **per-IP 10 requests / 15 min** (fixed window) and a **global 200 requests/day** (day boundary in ET, same idiom as the system-prompt date). `handleChat(body, clientIp)` calls `checkChatLimit` **first — before the key check and before validation** — so the 429 paths stay verifiable without a key (no paid requests) and a misconfigured deploy is still protected; rejected 400s intentionally consume budget too. Both limits return **429, never 503**, because the client special-cases 503 as "Chat isn't configured" — the distinct friendly messages surface as inline error bubbles with zero client changes. The client IP comes from the first `x-forwarded-for` entry via the shared `clientIpFrom` helper (missing/empty → an `'unknown'` bucket), called in each wrapper since header access is the only framework-specific part. Expired IP windows are pruned on every check so the Map can't grow unbounded. Counters are module-scope: a hard guarantee on the long-running k8s process, **best-effort on Vercel** (per-instance, resets on cold start — same tradeoff as the odds cache); the real backstop is the monthly spend limit on the Anthropic key. Note `vercel dev` spawns a fresh process per invocation, so the limiter never appears to trigger there — that's an emulation artifact, not a bug; on real Vercel a warm instance holds the counters (verified in production: 10 allowed, then 429). Vercel also **prepends the real client IP** as the first XFF entry, so a forged `x-forwarded-for` can't buy a fresh bucket there — the spoofing caveat only applies to hitting the k8s backend directly via NodePort. To exercise the limiter without spending anything, send invalid bodies (`{"messages":[]}`): the limit runs before validation, so 400s consume budget but never call Anthropic.

**Daily briefing:** `src/components/DailyBriefing.tsx` renders a collapsible beat-reporter card (headline always visible, click to expand the recap paragraphs) mounted between `HeroStrip` and `Nav`. It reads a **static file**, not an API: `public/briefing.json`, fetched with `cache: 'no-cache'` so a fresh push isn't masked by a cached copy. That file is **written by the daily-beat-reporter routine — never hand-edit it**; the contract and the routine's prompt both live in `docs/routines/daily-beat-reporter.md`. Like `HeroStrip`, the card renders nothing on any failure (missing file, malformed JSON, wrong shape). It also renders nothing when the briefing's `date` is **more than 48h behind today** (computed in `America/New_York`, same idiom as `buildSystemPrompt` in `chat.ts`), so a skipped or failed routine run degrades to an absent card instead of presenting week-old copy as news. The routine's push auto-deploys Vercel production (see Automated routines), so production should always be within the window; if the card is missing there, runs have been failing. k8s lags until the next `pipeline.sh` and past 48h drops the card rather than showing an old briefing.

**On this day:** `src/components/OnThisDayCard.tsx` is a near-clone of `DailyBriefing` — same collapsible card, same `cache: 'no-cache'` static-file read (`public/on-this-day.json`), same render-nothing-on-any-failure behavior, same staleness cutoff — showing a verified Phillies game from today's month/day in a past season. Written by the on-this-day-reporter routine (`docs/routines/on-this-day-reporter.md`); **never hand-edit the JSON.** It's mounted in `App.tsx` stacked directly **below** `DailyBriefing`, fully independent: its own fetch, its own collapse state, and it self-hides without disturbing the briefing above it. Gated by the `enableOnThisDay` LaunchDarkly flag, defaulted `true` in the `useFlags()` destructure so an unreachable LD client preserves current behavior — same kill-switch pattern as `enableDailyBriefing`. The schema carries **two** dates and conflating them breaks the card: `date` is the ET day the routine wrote the card (drives staleness, exactly like `Briefing.date`), while `historicalDate` is when the game actually happened and is decades old **by design** — never measure staleness against it. The shared date helpers both cards use (`easternToday`, `daysBehind`, and the noon-anchored `formatDate`, which avoids the bare-`YYYY-MM-DD`-parses-as-UTC-midnight day-shift) live in `src/utils/date.ts`.

**Playoff Push:** `src/components/PlayoffPush.tsx` is the pennant-race panel at the top of the Standings tab — wild card position (IN/OUT vs the NL's 3 berths, margin to the cutoff, elimination number), division position (GB, magic **or** elimination number), and a footer with games left, home/away split, strength of remaining schedule, and the current pace projected out. Added 2026-08-13 because the app was already fetching `eliminationNumber` and `wildCardEliminationNumber` on every Standings load and discarding both.

Three things here are load-bearing. **First, it shares `WildCardStandings`' ordering rather than deriving its own**: the fetch-and-tiebreak moved into `src/hooks/useWildCardRace.ts` (lifted verbatim from that component), which `Standings` owns and spreads into both children. Two copies would double the per-tied-club `fetchSeasonResults` round trips and, worse, could drift — a panel claiming 4th directly above a table showing 3rd is worse than either number alone. **Second, it takes `divisionRecords` as a prop** from the `fetchStandings` call `Standings` already makes, so it adds no duplicate standings request, and it's mounted outside that fetch's loading/error branches (same independence convention as `WildCardStandings`), returning `null` when the Phillies aren't in the records. **Third, a 0.0 margin is a tiebreaker, not a rounding artifact** — on 2026-08-13 the Phillies were tied 64-58 with Arizona and lost the head-to-head 1-2, so the panel says "Tied with D-backs; D-backs holds the tiebreaker" and surfaces the note `applyTiebreakers` already produces, rather than printing a bare "0.0 back" that reads like a bug.

Two new trimmed fetches in `src/api/mlb.ts`: `fetchRemainingSchedule()` (same endpoint and `fields=` idiom as `fetchSeasonResults`, filtered to non-`Final` games) and `fetchLeagueRecords()` (**both** leagues, `leagueId=103,104` — the remaining schedule includes interleague games, so an NL-only map would leave strength-of-schedule with unknown opponents). They're fetched in separate `.then` chains, not a `Promise.all`, so a strength-of-schedule failure doesn't take the games-left figure down with it. **Games remaining is counted from the schedule, never from `162 - (W+L)`** — a tie or suspended game makes the schedule carry more `Final` games than the standings show decisions for (123 vs 122 on 2026-08-13), so the subtraction is off by one.

The math is the pure `src/utils/playoffPush.ts`. Note `clinchNumber()` exists because MLB sends the string `"-"` — not `null`, not an absent key — for a clinch figure that doesn't apply, so `Number()` alone renders `NaN`. **The panel deliberately shows no playoff probability**: that requires simulating the rest of the league, and anything less is a fabricated number wearing false precision — the same standard the beat-reporter and on-this-day routines are held to. Every figure shown is either read straight from MLB's response or arithmetic a fan could redo by hand. No backend, dependency, DB, or flag change.

**Matchup preview:** `src/components/MatchupPreview.tsx` is the pregame panel at the top of the Schedule tab — the two probable starters head to head (season ERA/W–L/IP/K/WHIP plus a "Last 3" line aggregating their most recent three starts), with the game's odds in the footer. Added 2026-08-13 to fill the one gap in the app's game-day arc: past games had `GameDetailModal`, live games had `LiveGameStrip`, and the future had only `HeroStrip`'s opponent-and-time line.

Three things here are load-bearing. **First, it fetches no schedule or odds of its own** — `Schedule` already has both, picks the first `Preview`-state game dated today or later, and passes it down with its resolved odds, the same arrangement as `PlayoffPush` taking `divisionRecords` from `Standings`. It keys on `Preview` rather than non-`Final` because once first pitch is thrown the panel's job belongs to `LiveGameStrip`. **Second, `hydrate=probablePitcher` on `fetchSchedule` returns only `{id, fullName, link}`** — no stats — so each starter still needs `fetchPitcherSeason` (new; season line for *any* player, since `fetchPitchingStats` is scoped to `teamId=143` and the opposing starter is the whole point) plus `fetchGameLog`. **Third, MLB doesn't post probables until roughly two days out, so "no probable announced" is the normal state, not an error**: with neither side announced the panel renders `null` (it would otherwise show "TBA vs TBA" over an empty table, strictly less than HeroStrip already gives), with one announced the other column is TBA and dashes. Each starter's two lookups also degrade to nulls independently, so one dead pitcher lookup can't blank the other side.

**Every stat cell is styled identically, and deliberately so — don't add a "who has the edge" highlight back.** The first version emphasized whichever pitcher had the better ERA and drew it in `phillies-red`, which meant the *opponent* lit up in the club's own brand color whenever he was outpitching the Phillies; it read as "this is the Phillies' number" rather than "this is the better number", and red independently reads as "bad" in a stat table. Re-doing it in bold instead was rejected too: picking a winner per row editorializes on a panel whose job is to set the two lines side by side and let the reader compare them.

The aggregation is the pure `src/utils/matchup.ts`. Note it filters the game log on `gamesStarted === 1`: a log mixes in relief outings, and one mop-up inning would count as a "start" and misrepresent the workload in the role being previewed. Innings math goes through the new `src/utils/innings.ts` because **MLB's innings-pitched notation is not decimal** — `"6.1"` is six innings and one out, so `5.2 + 5.2` is `11.1`, not the `11.4` that float addition gives. That module is now the single source of truth for the notation; `src/utils/trends.ts` had its own private `parseInnings` and now imports `inningsToFloat` from it. Gated by the `enableMatchupPreview` LaunchDarkly flag, defaulted `true` in the `useFlags()` destructure — **the flag does not exist in LaunchDarkly yet**, so it currently always renders; create it there to make it togglable. No backend, dependency, DB, or secret change.

**Bullpen usage:** `src/components/BullpenUsage.tsx` is the workload panel at the top of the Pitching tab — trailing-7-day appearance counts, pitch totals, innings, days of rest, and descriptive flags (`3 straight days`, `back-to-back`, `109+ pitches last outing`), split into a Bullpen group and a Rotation group. Added 2026-08-21 to close the one blind spot left in the game-day arc: nothing in the app showed that a reliever had thrown on three consecutive days, which is the single most predictive fact about how a late inning goes.

Two things here are load-bearing. **First, it deliberately reports workload rather than predicting availability** — no `LIKELY UNAVAILABLE` badge, no color-coding a pitcher as "tired." Same standard `MatchupPreview` and `PlayoffPush` already hold themselves to (no per-row "who has the edge" highlight, no fabricated playoff probability): whether a reliever pitches tonight depends on score, leverage, and private training-staff info this app doesn't have, and a confident verdict next to a measured `numberOfPitches` would read as equally authoritative when it isn't. The panel states facts (`3 straight days · 34 pitches`) and lets the reader draw the conclusion. Spot-checked against the real 2026-08-21 vs. Cardinals game day: every reliever showed 2+ days of rest (Bowlan and Duran the shortest at 2), and the two flagged pitchers (Kerkering's `3 straight days`, Raley's `back-to-back`) had both stretches end on 8/18 — three days prior, not today — so the Rest column already told the true story and a reader correctly concluded the whole bullpen looked available without the panel having said so.

**Second, the active roster cannot distinguish starters from relievers** — verified against `/teams/143/roster?rosterType=active`: every active pitcher comes back `position.type: "Pitcher"`, with no SP/RP field anywhere. Role classification instead comes from season splits (`gamesStarted / gamesPlayed >= 0.5`), which is why `BullpenUsage` takes `seasonSplits` as a **prop** from `PitchingTable` (which already calls `fetchPitchingStats()`) rather than fetching them a second time — the same no-duplicate-fetch arrangement as `PlayoffPush` taking `divisionRecords` from `Standings`. Because that prop is usually still `[]` on `BullpenUsage`'s first render (its own network chain often resolves before `PitchingTable`'s fetch does), classification is a `useMemo` over `[appearances, roster, seasonSplits, today]` — reclassifying for free when the real splits arrive — rather than baked into the one-time fetch effect; getting this wrong silently misclassifies every idle starter as a reliever until the next full remount. When season splits aren't available for a player at all (call-up, or just not loaded yet), classification falls back to whether any outing *in the window itself* had `gamesStarted === 1` on its boxscore line — a fallback only, since a reliever's single spot start would otherwise misclassify him for the rest of the window.

This required one small refactor to `PitchingTable.tsx`: it used to `return` early on loading/error before rendering anything, which would have taken the panel down with a season-stats failure. It now follows the same single-`return`-with-inline-ternary shape `Standings.tsx` already uses for `PlayoffPush`/`WildCardStandings`, so `BullpenUsage` mounts and fails independently.

Data: one `fetchSchedule` call for the trailing 7 ET days (via the new `shiftDate` helper in `src/utils/date.ts` — pure Y/M/D arithmetic through `Date.UTC`, never local-timezone `Date` math), then one `fetchBullpenBoxscore` per `Final` game (new sibling of `fetchBoxscore` in `src/api/mlb.ts`, same `/game/{pk}/feed/live` v1.1 route, narrower `fields=` — ~22KB/game) via `Promise.allSettled` so one dead game degrades the window rather than blanking it, plus `fetchRoster()` so a pitcher with zero appearances still gets a row (the fresh arms are the point, not noise to omit). All pure grouping/classification/flag logic lives in `src/utils/bullpen.ts`, reusing `inningsToOuts`/`outsToInnings` from `innings.ts` (never sum MLB's non-decimal innings notation directly) and `daysBehind` from `date.ts`. Renders `null` on a failed schedule fetch or an empty window (off-season, All-Star break) — same self-hiding convention as `HeroStrip`/`MatchupPreview`. Gated by the `enableBullpenUsage` LaunchDarkly flag, defaulted `true` in the `useFlags()` destructure. The LD flag key is `enable-bullpen-usage` (created 2026-08-21, boolean, temporary) — **unlike `enable-game-detail`/`enable-daily-briefing`/`enable-on-this-day`, its targeting is still OFF in both environments**, which is the opposite of those three: a flag created OFF serves `offVariation` (`false`) to every LD-connected client, so until someone flips targeting on in production the panel is actually hidden for any user whose LD client connects successfully — the `= true` code default only rescues the unreachable-LD case, not an explicitly-off flag. No backend, dependency, DB, or secret change.

**Auth (email/password sign-in):** the app's only stateful feature and its only database user. `src/components/AuthWidget.tsx` is a modal (not a persistent panel like `ChatWidget` — signing in is occasional) rendered inside `Header.tsx`, which gained `user`/`onAuthChange` props and a `justify-between` row for it. The "am I signed in" state lives in `App.tsx`, not the widget, so future features can gate on it; it's populated once per page load by `fetchCurrentUser()` (`src/api/auth.ts`) in a `useEffect` mirroring the existing `fetchConfig()` one. **The session cookie is httpOnly, so asking the backend is the only way to know who's signed in** — there is no client-readable token, and nothing auth-related is in `localStorage`. Four routes, all in `server/src/auth.ts` following the same framework-agnostic `RouteResult` contract as `handleChat` (so `app.ts` and `api/index.ts` call them unchanged): `POST /api/signup` (201/400/409/429/503), `POST /api/login` (200/400/401/429/503), `POST /api/logout` (**always** 200 + a clearing cookie, even with no cookie or a dead DB — logout must never fail client-side), and `GET /api/me`. `/api/me` **deliberately breaks the 503-when-unconfigured convention every other route follows**: it returns `200 {"user": null}` for every failure including a missing `DATABASE_URL`, because it's polled on every page load to decide whether the header says "Sign In", so it has to fail soft like `fetchConfig` rather than surface an error the frontend must special-case. Sessions are **DB-backed opaque tokens, not JWT** (a real shared Neon DB now spans both deploy targets, which removes the usual stateless-token argument, and this buys instant revocation with no signing-key management): a 256-bit `randomBytes` token goes in the cookie, only its sha256 lands in `sessions.token_hash`, so a database leak alone hands out no live sessions. Passwords use `node:crypto`'s `scrypt` with a per-user 16-byte salt stored as `"<saltHex>:<hashHex>"` — **no bcrypt/argon2/jsonwebtoken/zod dependency was added anywhere**, matching this repo's hand-rolled style. Two anti-enumeration details that look like redundancy but aren't: `verifyPassword` is awaited even when no user row matched (it hashes against a fixed dummy so response timing can't reveal which emails exist), and wrong-password and unknown-email both return the identical `401 invalid email or password`.

**Auth schema and rate limiting:** `server/migrations/001_users_and_sessions.sql` is the whole schema — a plain `.sql` file, no ORM or migration runner, applied once with `npx neon psql -- -f server/migrations/001_users_and_sessions.sql` (**`psql` is not installed on this machine**; the Neon CLI's embedded fallback is what makes that work). `users` and `sessions` follow the repo's conventions: UUID PKs, `TEXT` not `VARCHAR`, `deleted_at` soft deletes, and **no FK constraints** — `sessions.user_id` is a plain `uuid`, so `getCurrentUser` does two queries rather than a join and tolerates a missing user row. Emails are stored trim+lowercased and uniqueness is a **partial** index (`WHERE deleted_at IS NULL`) so a future account-deletion feature could free the address. `server/src/authRateLimit.ts` mirrors `rateLimit.ts`'s in-memory fixed-window pattern but is stricter (5/15min login, 5/hour signup) and keys login by **both IP and email independently** — IP alone misses credential stuffing spread across hosts at one victim, email alone misses one host spraying many accounts. A **successful** login clears both buckets, so a legitimate user isn't locked out of their own account minutes later; brute force never reaches that path since it never produces a correct password. Same k8s-hard/Vercel-best-effort caveat as the chat limiter and odds cache. `server/src/db.ts`'s `getPool()` re-reads `DATABASE_URL` every call (so a late-added secret is picked up) but builds the `pg.Pool` once lazily, since a Pool is stateful; it registers a `pool.on('error')` handler because an unhandled idle-client error would kill the process.

**Cookies on the backend:** `RouteResult` gained an optional `cookies?: string[]`, the first response-header support anywhere in this backend — `reply()` in `app.ts` appends each via `c.header(..., {append: true})` and `send()` in `api/index.ts` passes the array to `res.setHeader`. Strictly additive: every pre-auth route omits the field and is untouched. `server/src/cookies.ts` owns the syntax, and its `isHttpsFrom(x-forwarded-proto)` exists for a concrete reason — **`k8s/base/ingress.yaml` has no TLS section**, so hardcoding `Secure` would make the cookie silently unsendable in-cluster (browsers drop `Secure` cookies from non-HTTPS responses) while working fine on Vercel; deriving it per request is correct on both and upgrades itself if TLS is ever added.

**Favorite players ("starring"):** the first feature to *use* the account primitive rather than just ship it. Signed-in users star players from the Batting/Pitching tables; stars persist in `favorite_players` (`server/migrations/002_favorite_players.sql`) and surface in `FavoritesCard` ("Your Players"), mounted between `HeroStrip` and `DailyBriefing`. **Signed-out visitors see the app exactly as before** — no stars, no card, and the tables' sticky Player column keeps its original `min-w-36` (it widens to `min-w-44` only when signed in, because the star eats ~22px and wrapped most names onto two lines at 375px). Three routes in `server/src/favorites.ts`, same framework-agnostic `RouteResult` contract as `auth.ts`: `GET /api/favorites`, `POST /api/favorites/add`, `POST /api/favorites/remove`. Both mutations are **idempotent and return the full updated list**, so the client replaces state from one authoritative response instead of merging. They authenticate via `resolveSessionUser(pool, token)`, extracted out of `getCurrentUser` in `auth.ts` (which is now a thin wrapper over it). Unlike `/api/me`, these routes **do not fail soft** — an invalid session is `401 { error: 'sign in required' }`, because `/me` only fails soft since it's the thing that *decides* sign-in state, whereas favorites is called once that's already known; the client's `fetchFavorites` still degrades to `[]`. Two schema details that look wrong next to `users` but aren't: the unique index on `(user_id, player_id)` is deliberately **not partial** (a partial one wouldn't conflict against a soft-deleted row, so every re-star would insert a duplicate instead of resurrecting via `ON CONFLICT … DO UPDATE SET deleted_at = NULL`), and `player_name` is a denormalized snapshot used only as a display fallback when a starred player is missing from the current season's stats. Cap is 50 per user, enforced so that re-starring an existing favorite *at* the cap still succeeds. Favorites state lives in `App.tsx` next to `user` — both tables and the card read it, and the tables unmount on every tab switch — and toggling is optimistic with rollback on failure. Note `favorites/add` and `favorites/remove` are the first non-MLB routes with a **second path segment**, so `api/index.ts` has to inspect `rest` as well as `segments[0]`. No new npm dependencies, no feature flag, and no deploy/secret change (`DATABASE_URL` and `pg` were already wired for auth) — only the migration needs applying.

**User profile:** the second feature to use the account primitive, and the first place identity — rather than just a key — becomes visible. Signed-in users edit a profile (display name, phone, hometown, favorite player/jersey number, fan-since year, avatar, three notification prefs) in `ProfileModal`, opened by clicking the avatar/name button that replaces the header's bare email span in `AuthWidget.tsx`'s signed-in branch. Data lives in `user_profiles` (`server/migrations/003_user_profiles.sql`), a table **separate from `users`** on purpose — `users` is the credential row read on every authenticated request, while profile data is nullable throughout, read on one route, and carries a ~20KB avatar; keeping them apart means a profile write can never touch a credential row. The row is created **lazily, on first save** — signup does not insert one, so `GET /api/profile` returns an all-null/all-false default profile (`DEFAULT_PROFILE` in `server/src/profile.ts`) for the normal case of a user who hasn't saved yet, and the client never has to distinguish "no profile" from "empty profile." Like `favorite_players_user_player_key`, `user_profiles_user_key` is **not partial** — saving is a single race-safe `INSERT … ON CONFLICT (user_id) DO UPDATE SET deleted_at = NULL`, and a partial index wouldn't conflict against a soft-deleted row.

Five routes in `server/src/profile.ts`, same `RouteResult` contract and same **not-fail-soft** `401`/`503` convention as `favorites.ts` (`GET /api/profile`, `POST /api/profile/update`, `/avatar`, `/password`, `/delete`) — the shared `authorize(sessionToken, feature)` preamble was extracted out of `favorites.ts`'s former private helper into `server/src/authorize.ts` so both modules use one implementation. `POST /api/profile/update` takes the **full editable field set, not a patch**, and its SQL column list deliberately **excludes `avatar_data_url`** — a name edit must never clobber the avatar, which has its own route and its own upsert. The avatar itself is a base64 `data:image/{png,jpeg,webp};base64,...` string in a plain TEXT column (capped at 200,000 chars server-side), not object storage — `image/svg+xml` is excluded from the allowlist because SVG is scriptable and this column renders straight into an `<img src>` in the app's own origin. `src/utils/avatar.ts` downscales any picked file client-side (`createImageBitmap` → `<canvas>` at ≤256px → JPEG q0.82, no dependency) before it's ever sent, landing around 15–25KB in practice; the server does not re-encode it, so trust in the bytes extends only as far as "renders in an `<img>` tag or fails to."

`POST /api/profile/password` reuses `auth.ts`'s `validatePassword` (now exported) and is rate-limited by a new bucket in `authRateLimit.ts` — 5 attempts / 15 min, **keyed by user id, not IP**, unlike every other bucket in that file, because these routes already require a valid session: the threat is a stolen/borrowed cookie brute-forcing the current password to lock the real owner out, and that attacker controls their own IP. On success it revokes every *other* live session for the account (`sessions.token_hash <> hashSessionToken(callingToken)`) while leaving the caller signed in.

`POST /api/profile/delete` is **the first multi-statement transaction in this backend**. Soft-deleting an account touches four tables — `users.deleted_at` (which frees the email via its existing partial unique index, the very thing that index was written for), every live `sessions` row, every `favorite_players` row, and the `user_profiles` row — and a partial failure would leave an inconsistent account, unlike every other single-statement write here where a partial failure is harmless. It uses an explicit `pool.connect()` → `BEGIN`/`COMMIT`/`ROLLBACK` → `client.release()` in a `finally`, because `pool.query()` calls can land on different clients and can't share a transaction. The response carries a clearing session cookie (same `serializeCookie` builder `logout` uses), so the browser is signed out in the same round trip.

Of the three notification preferences, two now actually send (see Notification emails below) and **`notify_game_reminders` is still stored but inert** — nothing in this app sends push or pre-game alerts. The modal says so, scoped to that one checkbox rather than the section: the blanket "we don't send anything yet" line that used to sit above all three became false the moment the daily email shipped, and a false disclaimer is worse than none. Profile state lives in `App.tsx` next to `user`/`favorites`, loaded in an effect keyed on `user` (clears on sign-out, refetches right after sign-in) — `Header.tsx` and `AuthWidget.tsx` both thread it through unchanged from how they already thread `user`. A successful account deletion calls `onAuthChange(null)`, which cascades through the existing `user`-keyed effects to clear favorites and profile in the same pass sign-out does. No feature flag (same call as auth and favorites — additive UI, invisible when signed out, can't break anything existing). No new npm dependencies anywhere in this feature.

**Notification emails:** the third feature built on the account primitive, and the first thing in this app that reaches a user when they aren't looking at it. One email per morning to each opted-in user, containing whichever of the two cards they asked for — `server/src/notifications.ts` reads the very same `public/briefing.json` and `public/on-this-day.json` the site's cards read, so the email can never disagree with the page. `server/src/email.ts` is the SendGrid Web API v3 sender (plain `fetch`, no SMTP client dependency, `SENDGRID_API_KEY` fail-soft exactly like `ANTHROPIC_API_KEY`/`ODDS_API_KEY`), and `server/src/emailTemplates.ts` holds the text and HTML bodies — inline styles on a single centered table, because Gmail strips `<style>` blocks and Outlook ignores most modern CSS.

**The trigger is a Vercel Cron entry in `vercel.json`** (`GET /api/notifications/daily`, `0 14 * * *` ≈ 10 AM ET), authenticated with `CRON_SECRET`. It is deliberately **not** the beat-reporter/on-this-day routines calling in after they push: cloud routine environments have **no secrets store** — their variables are readable by anyone using the environment — so a trigger secret parked there would be a secret in name only. 14:00 UTC also sits an hour after the later of the two routines (13:00), by which time Vercel has deployed the fresh JSON. Nothing calls the route on k8s; `CRON_SECRET`/`SITE_ORIGIN` are in `api-deployment.yaml` only so it can be exercised by hand there.

Four things here are load-bearing. **First, one combined email, not one per opt-in** — a user subscribed to both would otherwise get two emails seconds apart. The briefing supplies the subject line when it exists, because a decades-old on-this-day headline as the subject of a daily email reads like a mistake when today's game is also inside. **Second, the staleness rule is stricter than the cards'**: `DailyBriefing`/`OnThisDayCard` tolerate content up to 48h old, but `articleFrom()` requires `date === today` in ET and drops the section otherwise. A stale card is a page that needs refreshing; a stale *email* announces yesterday's game as today's news in an inbox where it can't be corrected. If both routines failed, nobody is mailed at all. **Third, `email_sends` (migration `004`) is claimed *before* the send, not written after it** — the loop inserts a `'sending'` row against a unique `(user_id, kind, send_date)` index and skips on conflict, so a cron retry, a manual curl, or both deploy targets firing cannot mail the same recap twice. A failed send flips the row to `'failed'` and the next run retries it, up to `MAX_SEND_ATTEMPTS`. **Fourth, unsubscribe is unauthenticated by design** — it is reached from an email, where the reader has no session and should not need one. The 24-byte token in `user_profiles.unsubscribe_token` (generated lazily, on first send) authorizes exactly one action for exactly one row. The route answers both GET (the footer link) and POST (mail clients' native one-click control, driven by the `List-Unsubscribe`/`List-Unsubscribe-Post` headers on every message) — a reader who can't find an unsubscribe button reaches for "report spam" instead, which is the fastest way to wreck a sending domain.

Two small additive changes ripple out of this. `RouteResult` gained an optional `contentType` — the unsubscribe page is the first non-JSON response in this backend, and a mail client opening that link needs a readable page, not `{"ok":true}`; both wrappers send `body` verbatim when it's set, and every other route omits it. And `user_profiles` gained `notify_on_this_day`, which `POST /api/profile/update` now **requires** in its payload like the other two booleans. The `unsubscribe_token` index is **partial** (`WHERE unsubscribe_token IS NOT NULL`), unlike `user_profiles_user_key` — every row predating the migration holds NULL there, and a plain unique index would permit exactly one of them. `email_sends` deliberately has **no `deleted_at`**: soft delete exists so a row can be hidden and later restored, and there is no such thing as un-sending an email.

**Env vars:** `SENDGRID_API_KEY` (the `notifications@allthingsphils.com` sender is already verified in SendGrid), `CRON_SECRET`, and `SITE_ORIGIN` (the canonical origin for the email's links and for reading the two JSON files; falls back to the request's own origin). All three must be set in the Vercel dashboard for the cron to do anything — a missing `CRON_SECRET` makes the route answer 503, and a missing `SENDGRID_API_KEY` makes every send fail. Free-tier SendGrid allows 100 messages/day, which `MAX_RECIPIENTS_PER_RUN` mirrors. No new npm dependencies, no feature flag.

**localStorage** is used for the `AllStarBanner` dismiss state (`phillies_allstar_banner_dismissed_2026`) — read/write is wrapped in try/catch to fail open if storage is unavailable.

**Styling** uses Tailwind v4 (CSS-first, no `tailwind.config.js`). Brand colors are `@theme` tokens in `src/index.css` — `phillies-red` (#E81828), `phillies-navy` (#002D72), `phillies-cream` (#FAF7F0) — used as `text-phillies-red`, `bg-phillies-navy`, etc.; don't reintroduce inline hex classes (the one exception is SVG attribute literals in `TrendChart.tsx`). The display font is Barlow Condensed (`font-display` token, self-hosted via `@fontsource/barlow-condensed` imports in `main.tsx`), and `.bg-pinstripe` in `index.css` provides the header's pinstripe texture.

**Linting** uses Oxlint (not ESLint) with React and TypeScript plugins. Config is in `.oxlintrc.json`.

**Deploy** targets are the local Docker Desktop k8s cluster (kustomize manifests in `k8s/`, ingress host `phillies-stats.com`) and Vercel — both host the same codebase permanently, not a migration. **Vercel production tracks the `develop` branch** (changed 2026-07-29), so any push to `develop` deploys production; k8s is the manual one, needing `pipeline.sh` to rebuild and roll out. The ingress routes `/api` to the backend Service and `/` to nginx — direct NodePort access (`localhost:30080`) bypasses the ingress, so `/api` 404s there and no data loads; use the ingress host.

On Vercel, `api/index.ts` is a single static serverless function handling all of `/api/*`, wired up via a `vercel.json` rewrite (`{ "source": "/api/:path*", "destination": "/api/index" }`) rather than a bracket-filename dynamic route. **Bracket-filename catch-alls didn't work on this project** — neither `api/[[...route]].ts` (double-bracket "optional" catch-all is a Next.js-only convention the plain Vercel Functions router doesn't recognize at all) nor `api/[...route].ts` (single-bracket catch-all, which on this project's router only ever matched exactly one path segment, treating `...route` as a literal non-special parameter name — `req.query['...route']`, not an array — so anything under `/api/mlb/*` 404'd before the function even ran). The `vercel.json` rewrite sidesteps file-name inference entirely: the `:path*` placeholder always arrives as a single slash-joined **string** in `req.query.path` (e.g. `"mlb/stats"`, not an array), which `api/index.ts` splits itself.

`api/index.ts` manually routes `/api/mlb/*`, `/api/odds`, `/api/config`, `/api/chat`, `/api/health`, `/api/signup`, `/api/login`, `/api/logout`, `/api/me`, `/api/favorites` (+ `/add`, `/remove`), `/api/profile` (+ `/update`, `/avatar`, `/password`, `/delete`), `/api/notifications/daily` and `/api/notifications/unsubscribe` to the same framework-agnostic functions the k8s backend uses: `server/src/core.ts` (mlb proxy, odds cache, config), `handleChat` in `server/src/chat.ts`, the four exports of `server/src/auth.ts`, and the five exports of `server/src/profile.ts`. Those shared functions take/return plain `{ status, body }` objects with **no Hono import** — `server/` and the repo root each do their own separate `npm install`, so each ends up with its own copy of the `hono` package, and mixing objects from two different copies of the same package in one bundle breaks (Hono's request/context types rely on module-scoped symbols that don't match across copies). `server/src/app.ts` is the only file that touches Hono — it wraps those same shared functions for the long-running k8s process (`server/src/index.ts` hands `app.fetch` to `@hono/node-server`'s `serve()`). The Vercel function types its request/response with small local interfaces over Node's built-in `http` types rather than depending on `@vercel/node` (that package pulls in Vercel's entire build toolchain — ~120 packages plus several transitive ReDoS advisories — just for two type shapes). Because `server/` has its own separate `package.json`, `@anthropic-ai/sdk` and `pg` are also listed in the root `package.json` purely so Vercel's root-level `npm install` can resolve them when bundling `api/index.ts` — intentional duplication, not a workspace migration. Vercel env vars (`ANTHROPIC_API_KEY`, `ODDS_API_KEY`, `DATABASE_URL`, `SHOW_ALLSTAR_BANNER`, `SENDGRID_API_KEY`, `CRON_SECRET`, `SITE_ORIGIN`) are set in the Vercel project dashboard, same keys as the k8s Secrets; all are optional/fail-soft so a Vercel deploy works without them, just without chat/odds/sign-in/daily email. Note `vercel dev` does **not** load `.env.local`, so auth and odds both 503 there unless you export the vars into its shell first — an emulation gap, not a routing bug. The `/api/odds` in-memory 30-min cache (in `core.ts`) is best-effort on Vercel (resets per cold start / per instance) vs. a hard guarantee on the long-running k8s process — accepted tradeoff, no shared cache store used.

To debug Vercel routing locally instead of guessing through redeploy cycles: `npx vercel link` then `npx vercel dev --listen <port>` runs an accurate local emulation of Vercel's actual routing/query behavior (unlike plain `vite dev`, which doesn't touch `vercel.json` rewrites or serverless functions at all).

The two images are deployed differently, permanently — not a migration in progress. The user's Docker Hub account is free-tier and can only publish one image, so only the frontend is registry-backed:
- **Frontend** (`phillies-stats`, root `Dockerfile`, nginx static) — pulled from Docker Hub. `k8s/base/deployment.yaml` uses `jsaviello1/phillies-stats:latest` with `imagePullPolicy: IfNotPresent` and `imagePullSecrets: dockerhub-creds`.
- **Backend** (`phillies-stats-api`, `server/Dockerfile`) — stays local-only by design. `k8s/base/api-deployment.yaml` uses the locally-built `phillies-stats-api:latest` with `imagePullPolicy: Never`.

`pipeline.sh` builds+pushes the frontend image to Docker Hub then builds the backend image locally (no push), restarting both Deployments after.

## Feature workflow (Spec-Driven Development)

Non-trivial features in this repo go through the `superpowers` SDD workflow, not ad-hoc edits:

- **Design specs** live in `docs/superpowers/specs/YYYY-MM-DD-<feature>-design.md`.
- **Implementation plans** live in `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`, broken into numbered tasks.
- **Progress ledger** is `.superpowers/sdd/progress.md` — tracks per-task completion, commit ranges, review status, and any accepted minor issues/deferred fixes for the in-progress feature. Check this file to see what's mid-flight and whether a task's review already surfaced known issues before re-deriving them.

Past examples of this pattern: `odds`, `schedule-team-logos`, `sortable-columns`, `all-star-banner`, `player-game-log` (see the matching plan/spec/progress entries).

## Testing

No automated test runner is configured. Instead, this repo uses the `webapp-testing` skill (`.claude/skills/webapp-testing/SKILL.md`) — a Playwright-based toolkit for driving the app in a real headless browser (navigate, click, screenshot, read console output).

**Every finished feature must be verified with `webapp-testing` before being considered done** — not just lint/typecheck. Use `scripts/with_server.py` to manage the `npm run dev` lifecycle, write a small Playwright script that exercises the actual user flow (click through to the changed UI, screenshot it, check for console errors), and confirm the result visually rather than assuming it works from source review alone.

Requires the `playwright` Python package and its Chromium browser binary to be installed locally (`pip install playwright && playwright install chromium`) — already set up in this environment as of 2026-07-08.

**Verifying chat changes costs real money** — every widget message is a billed Anthropic request against the user's key, so ask before sending one and keep the run to a single question. Most of a chat change can be verified for free first: the tools' trimming logic is pure, so replay it against real `statsapi.mlb.com` JSON (curl the endpoint, apply the same field picks) and check the shape before spending anything; the rate limiter has its own free path (see above). When you do run the widget, both servers must be up (`npm run dev:server` **and** `npm run dev`), and drive it via `aria-label="Open chat"` → the `Ask about the Phillies…` placeholder → Enter, reading the reply out of the `aria-label="Phillies chat"` dialog. Allow ~90s: a multi-tool answer under Opus is slow, and a short Playwright timeout looks like a failure when the request is merely still running.

## CI

`.github/workflows/ci.yml` runs on every PR into `develop` and on push to `develop`. Six independent jobs, each its own GitHub check:

- **frontend-build** — `npm ci && npm run build` (`tsc -b && vite build`). The main signal: nothing else in CI type-checks the frontend or proves it bundles.
- **frontend-lint** — `npm ci && npm run lint` (Oxlint).
- **backend-build** — `npm ci && npm run build` inside `server/`. Easy to forget this needs its own check: `server/` is a separate `package.json` with its own `tsc` build (see Architecture), and before this workflow nothing verified it compiled short of `pipeline.sh` or a live Vercel build failing.
- **dependency-drift** — `node scripts/check-dep-drift.mjs`, no install needed (it only reads both `package.json` files). Root `package.json` deliberately duplicates `@anthropic-ai/sdk` and `pg` so Vercel's root-level install can resolve them when bundling `api/index.ts` (see "On Vercel" below) — this catches the two copies drifting apart, which Vercel's build wouldn't error on, it would just silently bundle the stale version.
- **k8s-validate** — renders `k8s/base` and `k8s/overlays/local` with `kubectl kustomize` (pure client-side, no cluster needed) and schema-validates the output plus the standalone `k8s/monitoring/grafana-ingress.yaml` with `kubeconform`. Catches a broken kustomization or a malformed manifest before it reaches `pipeline.sh`.
- **secret-scan** — runs the open-source `gitleaks` CLI directly via its official Docker image (`docker run zricethezav/gitleaks:latest detect`) against the checked-out tree, **not** the `gitleaks-action` wrapper — that wrapper gates some repository-ownership types behind a paid license, and the plain binary needs none of that. `.gitleaks.toml` extends the bundled default ruleset with a narrow allowlist for confirmed false positives (verified by hand against the actual file each time one's added, `regexTarget = "line"` so the match isn't dependent on how much of the line a rule captures) — the first two entries are the `DISMISS_KEY` localStorage key name (`AllStarBanner.tsx` and its design doc) and a progress-log line narrating that a placeholder, not a real key, was appended to `.env.local`. Widen an entry only to the exact string that triggered it — never allowlist a whole path just to quiet the tool.

**What this doesn't cover:** there's still no automated test suite (see Testing above) — these jobs prove the app builds, lints clean, and ships no committed secret, not that any feature behaves correctly. `webapp-testing` verification before calling a feature done is still required and CI is not a substitute for it.

## Automated routines

**auto-merge-branches routine** (finds unmerged branches, opens/merges PRs into `develop`): only send a push notification when there's something actionable — a branch merged, a PR blocked on failing checks, a merge conflict, or an error running the routine. If the run finds no candidate branches or nothing to do, end the run silently; do not notify just to report a no-op.

**daily-beat-reporter routine** (`trig_01NEVfwEVHov4qXy2D7Wh4j8`, daily at 12:00 UTC ≈ 8 AM ET) writes the morning briefing and commits **only** `public/briefing.json` straight to `develop`. Its prompt is a thin wrapper that tells the cloud agent to read `docs/routines/daily-beat-reporter.md` from the checkout and follow it — so **edit the doc to change the routine's behavior**, and keep the routine's own prompt to invariants only, or the two will drift. Two things that doc encodes and must not be relaxed: every single-game stat comes from that game's boxscore (a player with an empty `stats.batting`/`stats.pitching` object did not play — the same trap the chat bot's `get_game_boxscore` exists to close), and incomplete upstream data means **commit nothing** rather than guess. **The push is the deploy:** Vercel's production branch was changed to `develop` on 2026-07-29, so pushing publishes production automatically — no Vercel CLI step and no token in the routine (deliberate: cloud environments have **no secrets store**, so variables are readable by anyone using the environment). The flip side is that a rejected push means nothing reached users, so the routine treats that as a failed run, saves the commit to a `claude/` branch, and says so in its final run summary. This is the one leg never yet exercised: cloud sessions guard pushes to non-`claude/` branches, and while `develop` is unprotected with no open PRs, it does carry `Claude`-authored commits. Note the production-branch change applies to **all** pushes to `develop`, not just the routine's — the integration branch now goes live. **Neither routine sends push notifications** — success and failure are both reported only in the run's own final text summary, never via a notification tool, so nothing about these runs reaches the user's phone.

**on-this-day-reporter routine** (`trig_01FRTs8tgq6MA8wRUY1XfrK7`, daily at **13:00 UTC ≈ 9 AM ET**) writes the historical card and commits **only** `public/on-this-day.json` straight to `develop`. Same thin-wrapper-prompt convention, same boxscore-only and commit-nothing rules, same push-is-the-deploy mechanics as the beat reporter. It runs in the **same** `phillies-stats` cloud environment (`env_016wMSZpYCdfkt239tXPmaHN`), so it inherits that environment's existing Custom network allowlist — no separate setup was needed (allowlists are per-*environment*, not per-routine; moving either routine to a new environment would require re-adding the hosts there). **The 13:00 slot is deliberate:** the beat reporter fires at 12:00 and ends by pushing `develop`, and two routines pushing the same branch concurrently means one push is rejected — which both docs treat as a failed run, not a retryable hiccup. Keep them an hour apart. Its one distinctive piece is the candidate search: ~60 single-day `/schedule` queries (one per season, `today.year - 1` back 60 years) for today's month/day, ranked no-hitter → walk-off → extra innings → blowout/shutout → anything, most-recent year breaking ties. The doc also encodes accuracy traps found while hand-verifying the seed card, all of which produced a wrong first draft: runner situations ("bases loaded", "scored from second") are play-by-play facts and can't be inferred from the RBI column; a 0-hit outing with a walk is *hitless*, not perfect; relief order must come from `pitchers[]` rather than being guessed; and game duration isn't in these endpoints at all, so "five-hour marathon" is fabrication.

Neither routine can run in the stock Default cloud environment: network access must be set to **Custom** with `statsapi.mlb.com` (and `allthingsphils.com`) added, because the Trusted allowlist covers package registries, GitHub, and cloud SDKs but no third-party REST APIs — every data fetch would otherwise fail with `403 host_not_allowed`. Both share the `phillies-stats` environment where that's already configured, so this is a per-environment setup, not something to redo per routine. k8s still needs `pipeline.sh` and so lags behind Vercel. Note `allthingsphils.com` is the custom domain fronting the same Vercel production deployment that used to be reached at `phillies-stats.vercel.app` — the `.vercel.app` URL isn't the one to allowlist or curl anymore.
